# Try the browser demo


1. Open [the demo](/#demo) and start a conversation.
2. Choose its terminal connection action. It supplies the host address and
   secret session token for that conversation.
3. Install Tress with the command shown on the website, or build from source.
4. Run the copied connection command. For example:

```sh
tress attach https://your-demo.example -s YOUR_SESSION_ID
```

The URL and ID above are placeholders. Use the values from your own demo
session. The `-s` value is an access token, not just a public thread ID. Anyone
holding that command can join the session. The demo validates it internally;
no external auth service or `createTressAccess` setup is required. A bare host
address selects its default thread; `-s` selects a Tress demo session.

Send a prompt from the terminal. Its response appears in both clients.
Add `--ui` to use the full terminal interface.

## A fresh session on refresh

Every page refresh starts a new demo session, even when the URL contains the
previous session ID. The header, browser URL, and copied terminal command all
use the new ID. Earlier threads remain available in the sidebar.

Opening a session link or selecting a sidebar thread resumes that conversation.
Reconnecting within the page keeps the current session. Terminals and connected
folders stay attached to their original session; copy the new command if you
want them to join the refreshed session. Refreshes count toward the demo's
session-creation limits. Hosts using `TRESS_DEMO_SHARED=1` keep a single shared
thread instead.

## Connect your computer or VM

The installer currently provides **v0.3.0**. Its `attach` command joins the
conversation; it does not share your machine's files. To connect files and chat
in one terminal, [build the source preview](#build-the-source-preview), open
**connect folder**, and run the command shown there on your computer or VM:

```sh
tress attach https://your-demo.example -s YOUR_SESSION_ID --ui
```

The default demo connects automatically. It has no pairing form or code-entry
step. The browser shows the connected machine, its permissions, and its files.
The same terminal opens the chat. Keep it running while using the files.
Access is read-only by default; add `--allow-write` for edits. Add
`--root /path/to/project` to restrict sharing to a folder, or `--chat-only` to
join without sharing files. Closing the connector stops file access while the
conversation remains available. Run the same command to reconnect.

## Build the source preview

Combined chat and file sharing through `attach`, including `--root`,
`--allow-write`, and `--chat-only`, requires the current source build. These
options are not in the published v0.3.0 binary. With Rust installed:

```sh
git clone https://github.com/assistant-ui/tress.git
cd tress
cargo install --locked --path crates/tress
```

If you already have the repository, use its current checkout. Run the binary
installed by Cargo (`~/.cargo/bin/tress` on macOS/Linux), or put that directory
before `~/.local/bin` on PATH. Both builds currently report `0.3.0`, so the
version string alone does not identify the source preview.

With that source build, run the copied `attach` command again. By default,
it offers the terminal machine's whole filesystem, read-only.
The session command connects directly in the default demo.
Use `--root /path/to/project` to restrict the
scope, or `--chat-only` to join without offering files. Whole-filesystem access
includes personal files your terminal can read, subject to OS permissions;
symlinks and special files remain unavailable.

Close the terminal to stop sharing. Run the command again to resume access.

```text
/status      show connection and host details
/disconnect  stop sharing and exit (chat-only mode can /reconnect)
/exit        leave the terminal client
```

Add `--ui` to use the full terminal interface:

```sh
tress attach https://your-demo.example -s YOUR_SESSION_ID --ui
```

To restrict sharing to a real project folder from your computer or VM, use:

```sh
tress attach https://your-demo.example -s YOUR_SESSION_ID --root . --allow-write --ui
```

Run it in the project folder. Once the terminal UI opens, both clients
can then ask the agent to read and edit that folder. Omit `--allow-write` for
read-only access. `/exit` or `/disconnect` stops sharing. No shell execution is
exposed, and switching chats requires exiting first. The site must be reachable
from the machine running the command; `localhost` always means that machine.

## Optional pairing and browser approval

Pairing remains available behind host environment flags:

| Host settings | Behavior |
| --- | --- |
| Both flags unset or `0` | Default demo: direct connection, no pairing controls |
| `TRESS_SHOW_PAIRING=1` | Adds **Have a pairing code?** under **connect folder**; modern `attach` still connects directly |
| `TRESS_REQUIRE_PAIRING=1` | Requires browser-owner approval and always shows the code form, even with `TRESS_SHOW_PAIRING=0` |

Both flags accept `1` or `true`. Change them on the server and restart or
redeploy it. Showing optional pairing does not change access permissions.
When pairing is required, enter the terminal's code in the browser before it
connects. Older hosts may also require this step.

On those hosts, the released v0.3.0 CLI can share a folder from a separate
terminal with `tress connect --site <host-url> --root .`. With optional pairing,
choose **Have a pairing code?** to enter its code. That legacy code-based
flow is hidden in the default demo; use the source-preview `attach` command
for its direct connection.

The public demo has its own access model. To connect an application you own,
follow [existing apps](/docs/existing-app); adding a URL alone does not make
an arbitrary chat website compatible.
